The database isolation check failed. The guardian could read another student's previously inaccessible Arcade owner ID. PostgreSQL also permitted planning a deletion of that student's contest-marked practice chart. The adult role already had invitation reads and gained permission to update another adult's invitation email. These were plan-only write checks against existing synthetic rows. The baseline guardian login already had reads across practice charts and the adult login already had reads across invitations. Table and column grants cannot impose an approved subject, row predicate or replacement value. The affected tables have no active row policy for these logins. Cleanup explicitly requires unfiltered evidence for readback and reports `access_required` if a row policy would filter it. A shared web, worker or administrative identity cannot be treated as an isolated Support login.
3. **At revision `c36choice001` with the tested permissions, end the review without issuing a grant.** Record the affected clearance categories as open. Reconsider application only if a separately authorized, database-enforced operation can bind an independently approved case to the exact subject, eligible rows and allowed changes while reading all required integrity evidence. First qualify that boundary on an equivalent disposable database as the actual logins. Require successful fresh and historical fulfillment, denial of unrelated reads and writes, protected-evidence checks, and an exact before-and-after ACL comparison. For any future change that passes, the DBA records the approved ACL difference and baseline, applies only that difference in one transaction and rolls back on verification failure.
