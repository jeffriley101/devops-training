# Verifier and director account deletion

Use this procedure for a verified adult asking to delete their own Woodshed sign-in. A parent asking for their child's deletion uses the [guardian procedure](parent-deletion-support.md). Both requests can start with an email to `support@woodshedwoodchuck.com`, without the app or the account PIN.

For a new confirmed request, use `execute-adult` in the [application-mediated procedure](parent-deletion-support.md#application-mediated-fulfillment). The independent approver assigns the operator to the case. The operator records the request and the trusted service performs the existing adult deletion. The direct commands below document the earlier executor and receipt format.

1. Open a restricted case, record its original clock and locate the adult's actual verifier record. Independently retrieve its email, numeric ID and creation timestamp. Verify the individual through a trusted channel and challenge the address recorded on that account. A message from the intake address, knowledge of student information, a claimed school role, or a receipt alone cannot establish ownership. For a shared or inaccessible mailbox, use an independently approved ownership check or leave the case open. Record only restricted evidence references.
2. Explain the scope to the verified adult. Check whether another adult needs to accept Program ownership and whether billing, invitations or private director access require action. The existing Program owner proposes transfer in Classroom management and the named successor accepts. Confirm the recorded owner actually changed. Have the billing owner resolve open checkout or renewal with the provider and verify the result. Ask the guardian or school to resolve ambiguous authority through its existing controls. When a beneficiary has an active seat or outstanding seat invitation, arrange continuity with the payer and beneficiary first. Billing staff reconcile pending payment events through the existing provider workflow. For an unbound private-director grant, the verified guardian can withdraw the specific director permission in the parent view. A pending explicit selection can also expire. For duplicate sign-in addresses, disputed control, or an owner unable to transfer, escalate for independent resolution. Keep the case open and preserve the original request date.
3. Obtain a fresh, explicit confirmation from the verified requester naming the case, this adult account, and the action `DELETE MY ADULT ACCOUNT`. The trusted approver publishes a case using `case`, `status`, `verifier_id`, `email` (canonical current address), `verifier_created_at`, `requester_ref`, `identity_ref`, `authority_ref`, `verified_by`, `verified_at`, `disputed`, `reviewed_by`, and `confirmation`. The confirmation contains `case`, `verifier_id`, `requester_ref`, `action`, `reference` and `at`. Use distinct opaque evidence references, verify authority within 24 hours and obtain confirmation within 30 minutes of execution. Revocation or dispute requires a hold under the case lock. Resolve disputes with a separate authorized reviewer and renew the evidence if the subject or authority changes.
4. A separate named executor uses the existing offline command and the adult-specific action. Use the restricted per-UID configuration in `/etc/woodshed/adult-deletion-support/`, adult approval files and a private durable register. Qualify the role and configuration against the intended database and existing revision, following the [trusted execution procedure](parent-deletion-support.md#approval-handoff-and-trusted-execution). The [PostgreSQL fixture](../tests/test_adult_deletion_support.py) lists the tested column grants for this executor. These include a lock on the billing account and insertion of the invitation revocation. Preserve the separate guardian and maintenance roles.

   ```bash
   python -m app.parent_deletion_support execute-adult <case-reference>
   python -m app.parent_deletion_support status-adult <case-reference>
   ```

5. After an interruption use `status-adult` to reconcile the existing intent. A receipt of `adult_deletion_applied` verifies the account operation against committed database state. Record it, any provider acknowledgments, outstanding exceptions and deadlines. A separate reviewer verifies the outcome and notifies the requester through the verified channel. A hold, a missing receipt or unresolved personal data stays open.

## Disposal of invitation revocations

Old Program invitations can create a new sign-in for the same mailbox. Deletion records a keyed digest of the former sign-in email in the existing session-revocation table for the seven-day invitation lifetime. The maintenance owner must run `app.session_revocations.purge_expired(session)` in a committed transaction against the qualified target at least daily and record the last successful run. Assign a named maintenance owner before use. A daily run removes an expired marker within the next 24 hours. The repository provides the expiry index and purge helper. Operation of a scheduled purge requires separate evidence. Restrict the separate case intent, including its keyed lookup value, to the existing Support retention period of 90 days after closure.

## Previously deleted adults

Use `cleanup-prior-adult` for spent tokens and attributable invitation contacts still linked to an already-deleted verifier. Open a new case under the same adult approval and register custody. Require the original adult deletion intent and receipt in that register. The executor checks the recorded database and role against its configuration, then verifies the receipt digest, account creation and deletion times, committed tombstone and any still-required invitation cutoff. Leave cases with a missing original record open.

The `accepted_invitation_contacts` result covers the recorded accepting adult, consistent acceptance dates through deletion, and addresses matching the original verified mailbox digest. `contact_review_required` means an actor-linked address remains after eligible matches were removed. This can happen when a prior mailbox key cannot be verified after rotation. `access_required` means the role could not complete disposal. Keep those cases open for the assigned reviewer. Student-owned recipient presets require independent attribution.

The independent approver publishes `case`, `status` (`approved`), `action` (`CLEAN UP PREVIOUS ADULT DELETION`), `verifier_id`, `verifier_created_at`, original `deleted_at`, `evidence_kind` (`support_receipt`), `deletion_evidence_ref` (the original case reference), `verified_by` and timezone-aware `verified_at`. Verify the original record within 24 hours of executing cleanup. The individual executor runs:

```bash
python -m app.parent_deletion_support cleanup-prior-adult <new-case-reference>
python -m app.parent_deletion_support status-prior-adult <new-case-reference>
```

A separate `prior_adult_spent_invitations_verified` receipt records the original deletion date and the later cleanup time. Original receipts remain tied to the cleanup scope their intent recorded. Keep any remaining contact, school, provider or other retention issues open.
