Classroom R6 S1 implementation note
=================================

Scope and release posture
-------------------------
S1 is an internal relationship foundation, disabled unless CLASSROOM_S1_ENABLED
is exactly 1. No public routes, navigation, templates, browser sessions, middleware,
email, payment services, PTA control, or student join operations are added. Schema
installation does not enable Classroom. Existing free Director behavior never
imports the service or tests its feature flag. Enabling the flag provides neither
paid entitlement nor student reporting.

The current release lacks a generic email-ownership proof mechanism for new
TrustedVerifier accounts. Direct new-email onboarding is therefore unavailable
for live users. The implemented onboarding service only creates synthetic local
identities, requiring an already credential-authenticated adult explicitly listed
in server-side CLASSROOM_S1_PROVISIONER_IDS, CLASSROOM_S1_LOCAL_PROVISIONING=1,
and an isolated /tmp/classroom-s1-*/... SQLite file or a literal loopback PostgreSQL
URL with a classroom_s1_ database name. Provisioned addresses must use .test or
.invalid, and Program provisioning verifies those synthetic actor/owner domains.
These checks contain local provisioning;
they do not constitute identity proof. No operator, account, or Program is seeded
by the migration or normal startup. Real direct onboarding remains blocked on an
approved independent proof mechanism, not a new student invitation requirement.

Identity and authentication
---------------------------
Adults remain TrustedVerifier IDs; registered students remain WoodchuckProfile IDs.
The service reuses validate_email, is_valid_pin, hash_pin, and existing
authenticate_trusted_verifier. Existing email always requires its own credentials;
onboarding cannot replace its hash/name or produce a login. A unique normalized
email arbitrates concurrent creation. Creating a synthetic adult adds only that
identity: no connection, profile, billing account, role, subscription, or consent.

AdultAuthentication is internal opaque evidence minted from current credentials,
bound to its SQLAlchemy Session and outer transaction, with no client actor-ID or
role adapter. Services recheck its credential hash against the database after
Program lock waits. A caller must authenticate again after commit/rollback. A
forged ID, Team Director capability, parent session, or child director emailed-link
session cannot supply this evidence. No existing browser authentication changes.
Future HTTP adapters require independent review of authentication, rate limiting,
Origin/CSRF, strict inputs, feature gating and no-store behavior. Existing Origin
middleware does not generally cover /trusted-verifiers; this patch adds no route.

Physical relationships and constraints
-------------------------------------
Eight additive tables provide the minimum independently retained records:

* classroom_programs extends Organization by primary key. Its NOT NULL restrictive
  owner FK is the one canonical Owner. Historical created_by_verifier_id and legacy
  organization memberships have no authority. owner_version invalidates proposals
  across successive transfers, including transfer away and back.
* classroom_role_grants preserves explicit head_director, admin, code_manager, and
  billing periods and end evidence. Compatible roles and multiple Programs work.
  Owner is not an independently removable role. Head Director and code-manager
  records represent responsibility only; code services remain S2. Billing cannot
  mark payments or activate access. Only Owner grants/revokes Program roles.
* classroom_classes has a stable ID, Program FK, and display name independent of
  codes. Owner/Admin can create Classes and assign/end teaching; neither role
  implies teaching. Other roles see Program metadata and only Classes they teach.
* classroom_teaching_assignments preserves explicit teaching periods, grant/end
  actors, and revoked/departed reasons. Teachers can record their own departure.
  Teaching grants no practice-verification, reporting, or enrollment capability.
* classroom_student_memberships uniquely anchors (Class, ordinary student ID).
* classroom_membership_periods preserves active/held segments and departed/changed
  endings on that anchor. Administrative hold is distinct from departure. There
  is no runtime insertion/join/import/suspension/reinstatement helper. Tests insert
  only synthetic relationships to demonstrate multiple Classes and period history.
* classroom_ownership_transfers stores the exact initiating Owner, recipient,
  owner version, pending/accepted/cancelled/superseded state, and resolution time.
* classroom_audit_events stores typed action, actor, target, Program/Class scope,
  relevant grant/assignment/proposal and old/new Owner references, server timestamp.
  No free-text payload, credentials, codes, tokens, parent or practice data.

Database constraints enforce referential integrity, non-null canonical Owner,
allowed roles/states/actions, positive periods, end evidence, unique membership
anchors, at most one open role/assignment/membership period, and one pending
transfer per Program. Composite FKs prevent assignment and audit scope substitution.
All new FKs use RESTRICT: hard deletion cannot silently erase authority/history.
A future membership service must lock the anchor and reject overlapping historical
periods; the database's open-period uniqueness is not a general overlap exclusion.
S1 has no service that writes student membership, so it cannot claim that workflow.

Authority operations and transactions
------------------------------------
The caller owns commit/rollback. Every Program authority mutation and its success
audit share a savepoint. New adult identity creation grants no Program authority
and does not fabricate a Program-scoped audit or consumer billing membership. SQLite explicitly begins a physical transaction before that savepoint,
so RELEASE cannot accidentally commit before the caller's outer rollback. SQLite
writes require foreign_keys=ON; the shared application engine is not changed.
SQLite is sequential local evidence, not a substitute for PostgreSQL row locks.

Management locks the Program first, then scoped Class/relationship/proposal rows.
Adult existence and credential reads are fresh but take no UPDATE row locks; S1
authority operations never mutate credentials. This avoids shared adults causing
cross-Program lock inversions; restrictive FKs retain the identity evidence.
One outer transaction may mutate only one existing Program. Provisioning locks the preexisting Organization before creating
its Program; it requires both authenticated local provisioner and exact founding
adult evidence. The founding adult becomes Owner and receives an explicit Head
Director grant only through this deliberate service, never by inference.

PostgreSQL writes require READ COMMITTED; stronger snapshot isolation is rejected
rather than allowing an old role snapshot after a lock wait. All authority checks
use refreshed Program state and database role predicates following acquisition. Transfer proposals require the current authenticated
Owner. Acceptance requires the exact recipient's independent credential evidence,
locks/reloads the Program and proposal, and rechecks owner/version/status/recipient.
A newer proposal supersedes the older one with an audit event. Pending proposals
have no token or email mechanism and remain valid only while their owner version
and pending status are current; S1 does not invent a timed public invitation flow.
Acceptance atomically replaces the canonical Owner, advances its version, resolves
the proposal and records old/new Owner audit references. Replays fail; no successful
audit survives a failed or rolled-back transfer. Independently granted roles remain
with the outgoing adult; powers derived solely from ownership disappear. Transfer
never duplicates Classes/memberships or grants teaching/reporting to the recipient.

No S1 adult management operation locks PTA, seasons, or student profiles. Existing
student anonymization locks PTA authority -> seasons -> profile and is unchanged.
It retains ordinary profile IDs; no Classroom path reads student data. Future
student enrollment/deletion integration must preserve that existing cross-system
lock order and reconcile Classroom restrictions before any live enrollment.

Dashboard boundary
------------------
director_sections delegates Connected Students to the unchanged dashboard_metrics
function and its existing free relationship/age/privacy calculations. my_classes
returns authorized administrative Program/Class metadata only: no student names,
counts, notes, charts, practice, games, or exports. Paid capabilities and reporting
are explicitly not_implemented. require_student_reporting always denies, even for
Owner/Admin/Teacher and even with a synthetic student membership. Class selection
requires its exact Program; unauthorized substitution fails. The disabled branch
performs no Classroom schema query. Missing schema while enabled raises an actual
schema error, never a legitimate empty roster.

Migration and preservation
--------------------------
The statically verified chain f19arcade001 -> p20team001 -> p21team001 now adds only
c22class001. No previous migration is modified. Existing PTA operator plan/stage/activation
commands retain their p21-only revision approval and reject c22 without mutation;
a separate PTA authorization is required before those operator commands can run
against a migrated database. Runtime and frozen-history preservation are tested
separately from that known operator limitation. All new tables begin empty; no
legacy row, owner, enrollment, entitlement, trial, sharing grant, cohort, Team,
contest attribution, C001/PILOT-D1, or PTA state is inferred or rewritten.
Downgrade checks every Classroom table first and refuses if any row exists; an
unused schema can be removed. No used authority/history is silently destroyed.

The existing p21 fixture created current Base metadata and stamped it as p21.
Its narrow update excludes Classroom tables and permits seeding an already truly
migrated database. Legacy migration comparisons now compare p21 metadata only.
All original preservation and security assertions remain. New migration tests use
actual p21 upgrades with populated synthetic data before applying c22class001.

Deferred contracts
------------------
Open S1 prerequisite: an approved independent identity-proof mechanism for live
direct adult onboarding. Synthetic provisioning does not satisfy that proof.
S2: entitlements, trials, packages,
codes/joining, enrollment/hold/departure workflows and account reconciliation.
S3: separately approved student capability/reporting/history authorization; no
speculative consent scopes or administrative-student projection exist here.
S4: Guest Classroom context and local Pristine integration; unchanged in S1.
S5: reconcile restored Owner/role/assignment/membership restrictions and audit
history with the external recovery process, including separately approved retention
and deletion handling. These audit rows are not an external restore-replay ledger;
there are no permanent tombstones, retention buffer, recovery or rollout claims.
R7: full director workflows, games, reflections, reports, exports, purchasing.

Validation commands, baseline failures/retries and final file hashes are recorded
outside the patch in the final response's temporary evidence manifest. No database,
credential, or generated test artifact belongs in the repository patch.
